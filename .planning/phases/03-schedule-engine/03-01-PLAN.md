<task type="auto">
  <name>Task 2: Write the adapter proposal</name>
  <files>.planning/phases/03-schedule-engine/FINDINGS.md</files>
  <action>
  Write `FINDINGS.md` with these sections:

  1. **Engine summary** — 1 paragraph.
  2. **Inputs the engine needs** — exact shape (active child, medications,
     administered doses, current time, rules).
  3. **Outputs the engine produces** — next eligible time per medication,
     or a flat list of upcoming doses with `(medId, when)`.
  4. **Adapter API proposal** — the exact signature `dosePlan.ts` will
     consume. Likely shape:
     ```ts
     function nextDoseFor(args: {
       medicationId: string
       childId: string
       now: Date
     }): { medicationId: string; at: Date } | null
     ```
     Justify the shape. If a different shape is more honest given the
     engine's actual behavior, propose that instead and explain.
  5. **What changes in `buildPlan()`** — pseudocode of the new flow. The
     `+2h` hardcode goes away; the alternation rule (last was Nurofen →
     next is Panadol) still lives in `dosePlan.ts` because that's an
     alternation policy, not a per-med rule.
  6. **What we can't do without code changes to the engine** — list
     anything the engine doesn't currently support that we'd need.
  7. **Test strategy** — what unit tests on the adapter will cover, what
     unit tests on `buildPlan()` will cover.
  8. **Risks** — anything that could blow up. Empty admin-dose list?
     A medication missing from rules? DST boundary?

  Length target: 200–500 lines including code blocks. If you need more, you
  have not understood the engine yet — read it again.

  Avoid: speculation about future schedule rules. Stick to what's in the
  code today.
  </action>
  <verify>
  File exists, sections covered, signatures are concrete.
  </verify>
  <done>
  FINDINGS.md ready for reviewer feedback.
  </done>
</task>
